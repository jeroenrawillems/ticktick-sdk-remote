### Bug Fixes

- [ ] **stdio mode swallows startup errors (found 2026-07-28).** With incomplete config, `ticktick-sdk stdio` dies with only `Error: unhandled errors in a TaskGroup (1 sub-exception)` on stderr and never shows the helpful `TickTickConfigurationError` text ("Configuration incomplete ... missing TICKTICK_*" naming the exact env vars). A Claude Desktop user gets no clue what to fix. Unwrap the ExceptionGroup in `main_stdio` (or log the real exception in the lifespan) so the actionable message reaches stderr. Found during the 2026-07-28 local re-verification, where the message only surfaced via a direct `validate_all_ready()` probe.
- [ ] **Filtered completed/abandoned/deleted listings still present a truncated window as complete (diagnosed 2026-07-27, the PA routine hit it around 07-24).** The 2026-07-22 saturation probe only works when no post-filter is active: the +1 probe task is the oldest task in the global fetch window, so a `project_id`/`tag`/`priority`/`kind` filter almost always drops it, `total` collapses to the filtered count and `next_offset` goes null, so a capped window looks like the complete result. Reproduced live on the deployed branch: completed + Physical, 2024-01-01 to 2026-07-27, returns `total=20, next_offset=null` (oldest row 2026-06-02), while a narrower 2026-04-01 to 2026-05-31 query alone finds 35 more Physical completions, and an unfiltered probe shows the underlying window is 501 tasks reaching back only to 2026-05-29 (very active account, the 500-task floor covers barely 2 months). Also makes the `limit` schema claim "'total' always reports the true count regardless of 'limit'" false for this case. Fix direction pending user choice: (A) detect saturation directly via `len(fetched) == fetch_limit` and emit an explicit truncation warning + `complete: false` flag, (B) additionally date-chunk walk older windows (move `to` below the oldest fetched `completed_time`, repeat until `from_date` or a polite call cap), which also fixes the silent stop at the 1000 cap for unfiltered deep paging, (C) reverse-engineer a per-project closed endpoint from a browser HAR capture (public libraries only document the global `/project/all/closed`, so its existence is unverified).
